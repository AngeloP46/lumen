# Lumen code review, 22 October 2026

Read-only review of main at 2eaba03 (SideStore 0.1.476): engine, editor, AI Denoise, Heal, masks, library,
canvas, diagnostics, plus a scan of the screens. Goal (Angelo): a bulletproof app with great performance before the
App Store; no deadline. Findings are ranked; each has the evidence and the fix. Nothing here is changed yet except
the two open PRs noted at the end.

## A. Freezes, crashes and lost work (fix first)

1. **The main thread can freeze while an AI model loads.** `LoadedModel` (Engine.swift) holds its lock for the whole
   load (seconds for the scene, depth or Heal model the first time). `release()` takes the same lock, and it is called
   on the main thread: the memory-warning handler, closing the editor (`EditorView.onDisappear`), `freeMemoryForHeal`,
   `export`, `healToolChanged`. If a model is loading on a background queue at that moment, the screen freezes until
   the load ends. Fix: loading happens outside the state lock; `release()` only drops the value and bumps a
   generation, so a load that finishes afterwards is thrown away. Never blocks.

2. **Photos imports copy each file on the main thread.** `importPicked` → `importAsset` → `add(copying:)` runs on the
   main actor and copies the whole RAW/ProRAW (50–100 MB) after writing it to a temporary file first, then reads its
   EXIF on the main thread too. Files imports were moved off the main thread on 19 Oct; Photos imports were not. Fix:
   write the asset straight into the library folder (or move, not copy, the temporary file) off the main thread,
   like `copyIn`.

3. **The photo is redrawn on every screen update.** `CanvasView.updateUIView` calls `setNeedsDisplay()` on every
   SwiftUI update of the editor, so any published change (AI Denoise progress after every tile, the histogram, busy
   text) re-renders the whole edited photo on the GPU. During AI Denoise this competes with the clean for the GPU.
   Fix: redraw only when the picture (`CanvasModel.update`), its placement or HDR mode changes.

4. **Editor observers are never removed.** `ensureDenoise` registers two NotificationCenter observers per opened
   photo and nothing removes them (only `memoryWarning` is removed in `deinit`). They hold weak references, so this
   is a slow leak and extra work on every app switch, not a crash. Fix: remove them in `deinit`.

5. **Shared "last result" variables are written from background threads.** `EditSession.healFailure`,
   `healDiagnostics`, `healAlpha`, `healModelReady`, `denoiseTimings` are statics set on worker queues and read
   elsewhere. Strings racing like this can crash in rare cases. Fix: return them with the result instead.

## B. Performance

6. **Brush masks are redrawn from scratch on every finger movement, on the main thread.** Each new point changes the
   brush's cache key, so `brushImage` repaints every stroke of that brush into a 1024 px bitmap inside
   `requestRender`. Long or many strokes make painting lag. Fix: draw only the new segment onto the stroke's bitmap
   while the finger is down; rebuild fully only when strokes are removed or feather changes.

7. **Moving the AI Denoise slider decodes the whole photo again.** The amount is applied in `decode`, so every change
   (after the 0.35 s rest) rebuilds the preview and its analysis layers, and the 100 % copy when zoomed in. Fix:
   keep the stored noise as a layer of the source and subtract it in `develop`: the slider becomes instant and no
   copies are rebuilt.

8. **The same AI work is repeated.** Each subject-at-a-point (Lens Blur focus, Subject masks) runs Vision's subject
   finder again on the whole photo, and subject, scene, depth and people each render their own 1024 px copy of the
   photo. Fix: run the subject finder once per photo and pick instances from the stored result; make the 1024 px copy
   once per photo.

9. **Every heal is blended over the whole picture.** `HealStore.apply` does a full-image `CIBlendWithMask` per heal,
   so 20 heals = 20 full-size passes in an export. Fix: blend each patch only inside its own square and composite it
   over the photo.

## C. Structure and code health

10. **EditorViewModel does too much (1,723 lines).** Loading, reloads, the 100 % view, the original copy, AI masks,
    AI Denoise, Heal, Remove people, presets, Auto, crop, export and history live in one class, coordinated by about
    fifteen flags (AI Denoise alone: `denoiseRequested`, `denoiseResume`, `denoisePausing`, `denoiseCancel`,
    `denoiseUserCancelled`, `denoiseTarget`, `denoiseWarming`, `denoiseProgress`). Most of October's bugs were
    combinations of these flags. Fix, in steps with tests: (a) `PhotoSources`: preview, 100 % copy, original copy,
    mask memo and their memory rules; (b) an AI Denoise job with one state value (idle / warming / running /
    paused / failed) instead of eight flags; (c) a Heal job the same way.

11. **Memory rules are scattered.** Free-memory thresholds of 700, 1300, 1500 and 2000 MB live in five places
    (`buildDetail`, `freeMemoryForHeal`, `export`, `warmDenoiseIfNeeded`, `HeavyWork`), next to `MemoryBudget`'s tiers
    and Denoise's own whole-read rule. Fix: one policy in `MemoryBudget` that everything asks.

12. **Dead code.** Heal's full-resolution texture path (`detailed`, `holeBox`, `mean`, kernels `lumenHealDetail` /
    `lumenHealEnergy`, ~130 lines) has been switched off since 18 Oct. It stays in git history; remove it from the app.

13. **Small things.** `healEnd` calls `freeMemoryForHeal()` twice. `bandWeights` (ColorCube) allocates an array per
    LUT entry (110,000 per curve/HSL change). The export sheet reads every selected photo's edits on the main thread to
    decide whether to offer HDR.

## D. Tests and process

14. **No fast logic tests.** CI has the engine test and a 75-minute UI suite, but nothing quick checks the rules that
    lose work if they break: reading old edit files (migration), paste and paste-some rules, undo history, preset
    application, memory policy. Fix: a small macOS command-line test (like the sandbox's ProGate test) that runs in
    seconds on every push.

15. **Known flaky UI tests** (pinch double-tap, before/after split drag, Lens Blur preview release) fail now and then
    and pass alone. Fix: retry a failed test once automatically and list which ones needed it, so real failures stand
    out. The sandbox's StoreKit test also needs a longer wait for products on a cold simulator (failed once at 10 s).

16. **Two branches kept in step by cherry-picking.** Every main fix is copied to sandbox by hand; one missed copy
    means the App Store build silently lacks a fix. Fix: bring main into sandbox with `git merge` instead of
    cherry-picks. The App Store code still never goes into main (Angelo's rule).
